# Agent Eval Results - 2026-06-10

First full real-agent eval round for issue
[#2](https://github.com/galjos/odh-cli/issues/2), run against the manual
protocol in [docs/evaluation.md](../../../docs/evaluation.md).

## Setup

- CLI: `0.2.5-dev`, commit `4aed99bf689d`, built from `main`, darwin/arm64.
- One fresh agent attempt per `tasks.json` prompt (12 independent LLM
  coding-agent attempts). Each agent received only the built binary, the skill bundle
  (`skills/open-data-hub-cli/SKILL.md`), and `recipes.json`. Agents were
  explicitly barred from reading `tasks.json`, repo source, and the web.
- Scored afterwards against `pass_criteria` and `common_failures` by a
  separate reviewer pass.
- Live upstream conditions during the round: the STA GTFS archive refresh
  timed out repeatedly (2m limit), so transit commands ran on the stale-cache
  fallback with warnings; `odh doctor` reported `tourism_openapi` HTTP 502
  while data endpoints stayed healthy.
- Smoke runner (`scripts/run-agent-evals.sh`): all checks passed, including
  recipe-shape validation.

## Failure Analysis And Fix Categories

Per the protocol, each issue is assigned a fix category.

1. Skipped origin discovery on the A22 task (1 occurrence).
   Category: docs or skill guidance. The skill should state more firmly that
   `odh mobility origins --station-type <type>` comes before any
   `--origin`-filtered query, even for "obvious" origins like A22.
2. JSON-default commands reject `--json` (2 agents hit exit-2 usage errors:
   `mobility origins`, `mobility stations`, `mobility events` reject
   `--json`/`--format` while the skill recommends adding `--json` before
   parsing). Category: narrow CLI feature candidate. Accepting `--json` as a
   no-op on always-JSON commands is a mechanical consistency fix; track it
   and apply if it recurs in the next round.
3. `mobility datatypes`/`stations` can truncate silently when `--limit` is
   hit before client-side origin filtering (one agent saw 14 of 48 datatypes
   at `--limit 1000` with no warning; `stations --limit 5` returned 0 Merano
   matches silently). Category: narrow CLI feature candidate. `mobility
   latest` already emits an "increase --request-limit" warning; datatypes and
   stations should warn the same way when `record_count == limit`.
4. No curated Tourism events query (the events data-quality task needed a raw
   `/v1/Event` call). Category: watch. One occurrence; the raw call worked
   and diagnostics already cover the caveats. Revisit only if agents keep
   needing `/v1/Event`.
5. German/Italian stop-name mismatch ("Sinich" vs "Sinigo"). Category: agent
   reasoning / upstream data. Consistent with the roadmap non-goal of
   hardcoded place aliases; agents recover via the other language.

No fix in this round justifies new natural-language command surface.

## Data Findings Worth Keeping

- A22 TrafficSensor flow/speed/emission datatypes are catalogued (45 types,
  ~300 stations) but return zero open rows for the core traffic metrics
  anonymously; only emissions-impact ratings and LinkStation rows are openly
  readable. The datatype catalogue oversells the open tier.
- ALPERIA EV availability had zero fresh active rows in 24h during the round;
  the only fresh South Tyrol EV row came from DRIWE-OCPI. The diagnostics
  `unavailable` verdict matched reality.
- EventShort `onlyactive=true` returned rows that all expired in January
  2018, all without GPS. `/v1/Event` looked healthy in the same window.
- Stale-cache GTFS fallback plus its warnings worked as designed under a real
  upstream outage.

precondition that issue [#4](https://github.com/galjos/odh-cli/issues/4) set
